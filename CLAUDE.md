### Embed interactions must never time out

Every embed button, dropdown, and other component interaction must be
acknowledged within Discord's interaction deadline, including before any slow
Riot API, chart-rendering, or database work.

### `/match` and `/livegame` are the announcements, not copies of them

Completed matches are one code path and live games are another, and the slash
command and the automatic announcement must each go through the same functions
in the same order.

Completed match — `announce.format_match` → `announce.build_announcement_embed`
→ `announce.MatchAnnouncementView` → `announce.remember_match_view_state`.
Callers: `/match` (`commands/match/match.py`), the match poller
(`tracker.poll_and_announce` → `announce.publish`), and `/selftest`.

Live game — `announce.format_live_game` → `announce.build_live_game_embed` →
`announce.LiveGameAnnouncementView` → `announce.remember_live_game_view_state`.
Callers: `/livegame` (`commands/player/profile.py`) and the live-game poller
(`tracker.poll_live_games_and_announce` → `announce.publish_live_games`).

Never write a second embed builder, view, dropdown, chart, or button set for
either surface. Never branch inside those functions on whether the caller is a
command or a poller. Never inline "just this one field" into a command handler.
Any change to layout, fields, dropdown options, charts, or buttons goes into the
shared function, so both surfaces change together in the same edit.

Where the two genuinely must differ, the difference is a field on the
announcement dataclass that the shared code reads, never a forked call path.
If a change cannot be expressed that way, say so and stop rather than forking.

Do not start or restart the bot solely because files have changed. When explicitly asked to run the bot, first stop every existing bot process, then start it with system Python 3.9.6 using `/usr/bin/python3 main.py`; never run `main.py` from `.venv`.

When you add or change a public slash command, update the `/commands` command directory with its current description and usage instructions. Keep owner-only commands out of that directory.
Keep each public slash command in its own command module named after the command (for example, `/champ` belongs in `commands/champ.py`). Move reusable logic shared by multiple commands into a separate shared module.

For any new command that requires a player, default to the account linked to the invoking Discord user when no player is supplied. For commands that require a match, default to that account's most recent match. Player-oriented commands should provide an optional `server` option plus a single combined `username` option (League or Discord username) so callers can select another account when needed; resolve it through `shared.resolve_username`/`target_for`, never separate `summoner`/`user` options.

Default embed layout for tabular data should follow `/jungleproximity`'s pattern: separate inline `embed.add_field` columns (name/label, then each stat) so Discord aligns the values automatically, rather than single-line text with inline markdown or manual padding.

Every Discord embed field value must be 1,024 characters or fewer. When a
tabular result can exceed that limit, split it at row boundaries into multiple
fields or pages before sending or editing the embed.

Automatic match announcements and `/match` must always render the same embed layout, fields, toggles, and buttons; keep them using the same shared rendering code rather than diverging implementations. The same requirement applies to automatic live-game announcements and `/livegame`.

Whenever functionality is added, changed, or removed, update the implemented-
features sections in both `AGENTS.md` and `CLAUDE.md`, keep their development
instructions synchronized, and update all affected docstrings before finishing
the task.

## Implemented features

- Automatic completed-match announcements have no queue filter: every completed queue a tracked player finishes (ranked, normals, ARAM, Arena, URF, bot games, customs, …) is rendered through the same shared renderer and persistent controls as `/match`, which passes `require_ranked_queue=False` on the same code path. Only Ranked Solo/Duo (420) and Ranked Flex (440) — `queues.RANKED_QUEUE_IDS` — do a rank lookup, report an LP swing, and record a rank-history point; every other queue is announced without any ranked LP lookup or rank-history change.

- Teamfight Tactics uses a completely separate `json/tft_data.json` account registry because TFT credentials resolve their own PUUIDs. Owner-only `/add` resolves the supplied Riot ID through both keys and stores/seeds the distinct League and TFT identities together; if the TFT half fails after League succeeds, it reports that partial result and directs the owner to `/tftadd`, which can also link a different TFT Riot ID. Owner-only `/tftupdate` processes every tracked League account, resolves each current Riot ID from its stored League PUUID through the League key, refreshes the separate TFT PUUID through the TFT key, and reports individual failures without stopping the remaining updates. When the resolved PUUID still matches the stored TFT registration it reuses that account's settled platform and already-seeded history instead of re-probing and re-seeding, which keeps the remembered match ids intact and drops the sweep from roughly five Riot calls per account to two; it edits its deferred reply with a running count so a long sweep is visibly alive rather than silent, and refuses to start while another sweep is in flight, since two concurrent sweeps doubled the Riot spend and left both silent past the point the owner restarted the bot. TFT then uses the same completed-match and live-game announcement pipeline as League: separately tracked TFT accounts are polled through TFT Match-V1 (Spectator-TFT-V5 live polling is disabled — see below), completed games show, in left-to-right embed columns, placement first, then player, level, and active traits (players-eliminated and player damage are deliberately not shown), plus — for Ranked TFT (queue 1100) — the LP each tracked player gained or lost since their previous ranked game, shown only on the announcement line exactly as League match announcements render it, with no LP embed column; the completed TFT announcement carries a persistent `Display` dropdown (like League match announcements') with `Players`/`Ranks`/`Traits` options that choose the middle embed column (the layout is always Place, that column, Level) by replacing the player-name column in place rather than trailing after Level: `Players` (the default) shows the name, `Ranks` shows every player's Ranked TFT standing (`Unranked`/`—` on no-rank/failed lookup), and `Traits` shows each player's active synergies; the rank lookup runs on demand only when `Ranks` is chosen, and the control is restored through the same `embed_button_states` path as League after a restart; the last-seen Ranked TFT standing per account lives in the TFT tracker state, and LP is attributed to a single game only when it is that account's lone new ranked game in the poll. Because the poller only ever learns that baseline as a side effect of announcing a ranked game — so the first ranked game after a fresh deploy showed no delta — `tracker.update_all_tft_rank_snapshots` runs once at startup (right after League's `update_all_rank_snapshots`) to seed `TftPlayerState.rank` for every tracked TFT account whose baseline is still missing, mirroring League and never overwriting a baseline a real game has already moved. That `ended X ago` timestamp is Match-V1 `game_datetime` directly — already the game-end time — with the game length no longer added on top of it, which had pushed the stamp a whole game into the future. TFT live-lobby announcements — both the automatic poll and the former `/tftlivegame` command — are disabled because Riot's Spectator-TFT-V5 endpoint returns HTTP 403 for the current TFT key, so `collect_new_tft_live_games` never succeeded; that collector and the shared live renderers (which list all up to eight participants, tracked players highlighted, each with their Ranked TFT standing — `Unranked` when genuinely unranked, `—` when the lookup fails) are kept so re-enabling is a one-line change in `poll_live_games_and_announce` once the key is authorized. TFT match and live-lobby deduplication uses separate state files, recording every match the poller actually fetched whether or not it produced an announcement, so an unformattable game is not re-fetched on every subsequent poll; only a failed fetch stays pending, since that failure is transient. A completed TFT announcement highlights just the tracked players actually present in that game, matching the live-lobby path, bolding that player's Place, Player, and Level cells; when Ranks or Traits replaces the middle column, that cell stays unbolded. Existing installations seed recent TFT history on first poll instead of replaying old matches. The shared TFT renderers read every field name Riot ships (`queue_id`/`queueId`, `game_length`/`gameLength`, `players_eliminated`/`playersEliminated`, `total_damage_to_players`/`totalDamageToPlayers`, and trait `style`/`tier_current`) and recover the hosting platform from the `PLATFORM_gameid` match id rather than defaulting to NA1, so a non-NA lobby's placement, level, eliminations, damage, traits, and names all populate; registered players resolve their `Name#Tag` from the TFT registry with no network call, and everyone else falls back to Spectator-TFT-v5's `riotId` before a regionally-correct account-v1 lookup. TFT commands are explicitly prefixed: `/tftmatch` renders that same shared announcement, `/tftmatchhistory` mirrors `/matchhistory` with up to 10 recent placements (level, eliminations, mode, an optional `queue` filter, and a top-4/bottom-4 score), while `/match`, `/livegame`, and `/matchhistory` remain League-only.
- The shared completed-match Items renderer recovers an ADC/BOTTOM player's latest timeline boot purchase when the final Match-V5 participant inventory no longer contains one; sale and undo events clear that fallback, while a bot-lane role-quest `ITEM_DESTROYED` event preserves the boot because Riot moves it into the dedicated role-quest slot. Any boot present in the final payload remains authoritative. Boot detection uses Data Dragon tags plus conservative fallback IDs, including current Gluttonous Greaves `3008` and Gunmetal Greaves `3172`, while regular Manamune `3004` remains a normal item; known boots stay visible with a name lookup or `🥾` fallback even when Data Dragon or a custom emoji is unavailable.

- Meetup planning (`bot_app/meetups/`, `/meetup propose|confirm|list|cancel`) runs as a
  two-axis poll that becomes a locked plan: `timeparse.py` is a pure parser turning
  comma-separated free text ("fri 7pm", "tomorrow 18:30", "9/5 7:30pm", "sept 6 8pm") into
  UTC epochs against an IANA zone, rejecting explicit past times while rolling a bare
  time forward to its next occurrence; `store.py` keeps meetups in their own
  `json/meetups.sqlite` (schema `user_version = 1`, tables `meetups`/`meetup_options`/
  `meetup_votes`/`meetup_answers`) rather than the prunable `matches.sqlite` cache, storing
  one row per (user, axis, option) vote so re-answering an axis replaces that member's
  selection and an empty selection is a real answer. Activities and times are polled as two
  independent multi-selects rather than one activity×time cross-product, which would exceed
  Discord's 25-option select cap; the organizer's `Lock it in` button opens an ephemeral
  picker defaulting to each axis' leader, and the locked embed's headcount is the *overlap* —
  members who ticked both winning options. `render.py` builds every state's embed from the
  meetup's own `state` field (one builder, no per-caller copies), renders times only as
  `<t:epoch:F>`/`<t:epoch:R>` so each viewer sees their local timezone, uses separate inline
  label/votes/voters columns, and clamps every field value to 1,024 characters. `views.py`
  answers each interaction from local SQLite inside the interaction deadline and persists only
  `{"meetup_id": …}` through the shared `embed_button_states` record, so a restored view
  reflects current votes rather than a snapshot; `bot_app/command_views.py` restores both the
  poll (`meetup`) and confirmation-ping (`meetup_confirm`) kinds.
- `/meetup confirm` is the deliberate double-check: it resolves recipients (expected but
  unanswered by default, optionally everyone expected or everyone who voted), shows the
  organizer an ephemeral preview of exactly who would be pinged, and only sends on a second
  click. Because editing a message never notifies anyone, the ping is a new message posted into
  the meetup's thread — mentioning a member there both pings them and adds them to the thread —
  and it is the one place in the bot that deliberately opts in to `AllowedMentions(users=True)`
  instead of suppressing mentions. Its buttons write into the same attendance store the locked
  poll message reads, so answering on either surface updates both, and re-running the command
  pings only whoever still has not replied.
- `/meetup propose` attaches a discussion thread to the poll message and pins it, keeping the
  embed itself in the parent channel because an archived thread cannot have its messages edited
  — a threaded embed would return from auto-archive with dead buttons. Threads use the maximum
  7-day auto-archive, are skipped when the command is run inside a thread (Discord has no nested
  threads), and missing Create Public Threads / Manage Messages permissions degrade quietly to a
  threadless, unpinned meetup rather than failing the command. `poller.py`'s
  `poll_and_close_meetups` runs on its own 10-minute task loop in `main.py` and, six hours after
  a meetup's start time (or 30 days after an unlocked poll was created), replaces the embed with
  a static summary, drops the controls, unpins, and archives *and locks* the thread rather than
  deleting it, since the discussion is what the thread existed to preserve.

- Owner-only `/add` takes an optional `user` and a `teammate` boolean (default false). A `summoner` with no `#Tag` defaults its tagline to `NA1`. With `teammate:True` it skips League/TFT tracking and instead registers a *teammate*: a bare PUUID stored in `bot_app/store.py` as `json/teammates.json` keyed by PUUID (with the `user` id as `discordId`, or blank/untied when `user` is omitted), cached like `tracked_puuids()` through `teammate_puuids()`. `user` is optional for normal tracking too: when it is omitted, `track_account`/`_track_both_accounts` key the League and TFT identities under one synthetic 18-digit sentinel id (`_next_unlinked_key`, matching the hand-written `000000000000000001` convention already in `data.json`), reusing that key when the PUUID is already tracked so a re-add replaces it in place; such an account still polls and announces like any other, it just never matches an `<@id>` mention. A teammate does resolve through player-oriented commands' `username` option: `shared._linked_target` (and so `resolve_username`/`target_for`) falls back to the teammate registry both for a `<@id>` mention of a teammate-only user and for the caller's own default target, and `_summoner_target` reads a teammate's stored server the same way it reads a tracked account's when a teammate is looked up by Riot ID. Called with a `user` but no `summoner`, `/add` switches that user's existing record between the registries instead of resolving anything: `teammate:true` demotes their tracked League+TFT account to a teammate (`_demote_to_teammate` → `untrack_account` + new `untrack_tft_account`), `teammate:false` re-tracks their teammate PUUID as a full account (`_promote_from_teammate` → `_track_both_accounts`) and drops the teammate entry, so a PUUID only ever lives in one registry. A teammate is *not* a tracked account — the match and live-game pollers never fetch its games and it never surfaces an announcement of its own. Resolution sweeps NA/EUW/KR and settles the platform with `home_platform` exactly as `track_account` does, but seeds no matches or ranks. `render.build_match_columns` bolds a teammate PUUID exactly like a data.json player, but only when that same lobby also contains a real tracked PUUID (`tracked_puuids()` or the announcement's `highlight_puuids`), so an all-teammate lobby stays unhighlighted. Live-game (`build_lobby_columns`) and TFT surfaces are unaffected. Removing a teammate is a direct edit to `json/teammates.json`.
- Every riot-id lookup sweeps NA1, EUW1, and KR (`routing.lookup_platforms`): a `server` option on any player-oriented command only decides which of those platforms is checked first. Because account-v1 is regionally routed but answers for every region, the riot-id call alone cannot say where an account lives, so the platform is then settled by `RiotClient.home_platform`, a summoner-v4 probe across the same candidates — without it an EUW or KR player resolved through the americas route was labelled NA1 and every per-platform call (mastery, ranks, level) came back empty. `/add` sweeps and probes the same way, storing the platform that actually hosts the account. A tracked account's stored server still wins over all of it. Every user-facing "not found" message on a command with a `server` option names the platforms that were searched, via `shared.searched_servers` (`not_found_embed`, plus `/duo`'s own message), and echoes back every option the caller actually supplied via `shared.supplied_options_text` — a **You entered:** trailer listing each filled-in option (user-typed options rendered as a non-pinging mention, blank ones omitted), or a note that nothing was supplied and the caller's own linked account was used, so a typo'd tag or a stale `username` option is visible in the failure itself. Player-oriented commands take a single `username` option instead of separate `summoner`/`user` options: a Discord mention (`<@id>`) is looked up as a tracked account directly via `shared.resolve_username`, and anything else is treated as a riot id/summoner name — so either kind of value works in the one field. Server options that select a region rather than look up a player (`/champ`, `/rotation`) are unaffected.

- Per-player match ratings in `bot_app/rating.py` (version 1.1, standard five-player Summoner's Rift only — ARAM, Arena, remakes, and malformed role layouts are left unrated), built only from fields the Match-V5 match and timeline payloads actually carry: no invented ward-quality, support-quest-timing, jungle-camp (as opposed to jungle-monster), isolated-death, or teamfight-presence signals. Normalization is corpus-relative rather than lobby-relative: gold/XP/CS checkpoint metrics are first expressed as a signed difference against the direct role opponent (the 10:00 level plus the 10:00→15:00 swing, not two near-duplicate levels), then every metric is standardized against a stored population mean and standard deviation for that player's own role, supplied by `bot_app/rating_baselines.py` from the `rating_baselines` table. That makes a score comparable across matches, lets a whole lobby be collectively good or bad, removes the systematic role bias lobby-wide z-scores produced (measured 1.22 points down to 0.03), and stops two-player metrics such as jungle-CS diff and the bot-lane duo diffs from collapsing to a magnitude-free ±1. Any `(role, metric)` the corpus has not yet seen at least 200 player-samples of falls back to the old lobby z-score for that metric alone, so a cold database still rates. Every accumulating total (healing and shielding, crowd control, bounties, steals, enemy jungle monsters) is expressed per minute, since a pooled corpus spans every game length. Economy uses a separate metric table per role family: lane roles (gold/XP/CS diff plus swing, GPM, CS/min), jungle (jungle-only CS diff plus swing, enemy jungle monsters per minute — never called a camp count), and support (bot-lane duo combined gold/XP diff plus swing, support GPM). Combat scores solo/outnumbered kills and multikills as two separately weighted metrics rather than one sum, which had let a single takedown count up to three times. Objectives credits epic-monster and structure participation only by explicit killer/assist credit, never by frame proximity. Discipline scores Riot's own time-weighted bounty surrendered, percentage of the match spent dead, and share of team deaths — no invented isolated/traded/objective-enabling death classification. Win/loss is deliberately excluded so the score measures individual play rather than the result; letter grades (S+ through F) and a Full/Limited confidence tag (Limited when the timeline couldn't be fetched, degrading every timeline-derived metric to a renormalised box-score-only rating with an explicit note) are assigned after scoring, with `SCORE_SPREAD` and `GRADE_THRESHOLDS` derived from the observed composite distribution instead of assumed (roughly S+ 2%, S 4%, A 9%, B 20%, C 39%, D 21%, F 6%). A Ratings option in `/match` and automatic match announcements' Display dropdown renders these scores as blue/red name/score/K-D-A columns, fetching the match's timeline on demand for the fuller metric set and falling back to the box-score-only rating if that fetch fails, carrying over whichever chart was selected and keeping its own Display/Chart dropdowns so the chart can still be changed and the view can be switched back to Players/Ranks/Rankings while ratings are shown.
- Rating population baselines in `bot_app/rating_baselines.py`, backed by the `rating_baselines` table (schema `user_version = 5`), which stores per `(patch, position, metric)` sufficient statistics only — sample count and running sums, never a per-game row and never player identity — pools them across the stored patch window, and withholds any baseline below the sample threshold or with no spread rather than dividing by a noisy denominator. Collection is manually triggered and costs no extra Riot requests: `lane_matchups.collect.harvest` records samples from the match/timeline pairs it already fetches, and `backfill_rating_baselines` rebuilds the box-score baselines from matches already in the cache, replacing each key's totals rather than adding to them so it is safe to re-run and leaves timeline-derived baselines untouched. Live announcements consume baselines but never write them, so no match is ever counted twice and a tracked player's own games cannot dominate the population they are scored against. Baselines age out on the same rolling patch window as the lane-matchup statistics.
